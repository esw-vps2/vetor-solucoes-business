# Bootstrap Administrador user on application start

## Context

Portal authentication from VETOR-003 requires a persisted user in PostgreSQL.
A new environment has no operator account, so the portal and authenticated
Swagger UI cannot be used until someone inserts a user by hand.

The requester asked the backend to create, on every application start, a
default admin user with password `god@2025` and an admin profile that can
access the whole system. Before creating, the backend must check whether that
user already exists. Follow-up decisions set the login email to
`admin@vetor.tech`, the home tenant to name `VETOR` and slug `vetor`, and
require the same seed in production.

The existing ABAC profile that grants all-tenant access is `Administrador`.
Users are unique by `tenant_id + email` and must belong to a tenant. Tenant
primary keys remain UUIDs generated by PostgreSQL. The slug `vetor` is the
stable lookup key for the home tenant.

## Desired outcome

When the NestJS process starts in development or production, it ensures the
bootstrap tenant `vetor` and the user `admin@vetor.tech` exist. If the user is
already present, startup continues without creating a duplicate and without
changing the stored password. If the user is missing, the backend creates the
home tenant when needed and then creates the `Administrador` user so an
operator can sign in and reach every portal capability and authenticated
Swagger.

## In scope

- On backend startup in development and production, check whether the
  bootstrap tenant slug `vetor` exists and whether the user
  `admin@vetor.tech` exists in that tenant.
- Create tenant `VETOR` / `vetor` only when that slug is missing. Let
  PostgreSQL generate the tenant UUID.
- Create the user only when `admin@vetor.tech` does not exist for that
  tenant.
- Assign profile `Administrador` and status `active` so ABAC grants
  all-tenant access.
- Hash the bootstrap password with bcrypt cost 12. Do not store the password
  in plaintext.
- Read the plaintext password from `BOOTSTRAP_ADMIN_PASSWORD`. Do not
  hardcode it in application source. The requested local value is `god@2025`
  and belongs only in environment configuration and the versioned example
  file.
- Update `infrastructure/.env.backend.example`, `docs/product.md`, and
  `docs/database.md` during approved delivery when those contracts need the
  bootstrap account recorded.

## Out of scope

- Changing login, refresh, logout, password recovery, or ABAC rules
- Changing tenant ids from UUID to numeric identifiers
- A public registration endpoint
- Resetting the bootstrap password on later startups when the user already
  exists
- Frontend UI for user provisioning
- Seeding additional non-admin users

## Acceptance criteria

- AC-001: On backend start, if tenant slug `vetor` is missing, the backend
  creates a tenant with name `VETOR` and slug `vetor`. If user
  `admin@vetor.tech` is missing in that tenant, the backend creates that user
  with profile `Administrador`, status `active`, and a bcrypt password hash
  from `BOOTSTRAP_ADMIN_PASSWORD`.
- AC-002: On backend start, if that user already exists in tenant `vetor`,
  the backend does not create another user and does not overwrite the stored
  password hash.
- AC-003: The created user can authenticate through the existing
  `POST /api/v1/auth/login` flow with email `admin@vetor.tech` and receives
  all-tenant ABAC access.
- AC-004: The plaintext bootstrap password is not hardcoded in application
  source. It is read from `BOOTSTRAP_ADMIN_PASSWORD`. Application logs do not
  print the password.
- AC-005: The same startup seed runs in development and production. Production
  must supply `BOOTSTRAP_ADMIN_PASSWORD` through environment or secret
  storage, not through application source.

## User experience

An operator starts the backend. If the bootstrap tenant or account is
missing, they are created before the process accepts traffic. The operator
signs in to the portal with email `admin@vetor.tech` and the configured
bootstrap password. Later restarts keep the same account and password hash.

## API and integrations

No new HTTP endpoint. Existing `POST /api/v1/auth/login` is the sign-in path.

Swagger, `openapi.yaml`, and `docs/api.md` do not gain a provisioning route.

Environment variables:

| Name                          | Workspace | Purpose                                                        |
| ----------------------------- | --------- | -------------------------------------------------------------- |
| `BOOTSTRAP_ADMIN_EMAIL`       | backend   | Bootstrap login email; value `admin@vetor.tech`                |
| `BOOTSTRAP_ADMIN_PASSWORD`    | backend   | Plaintext bootstrap password; local requested value `god@2025` |
| `BOOTSTRAP_ADMIN_TENANT_NAME` | backend   | Home tenant name; value `VETOR`                                |
| `BOOTSTRAP_ADMIN_TENANT_SLUG` | backend   | Home tenant slug; value `vetor`                                |

The example file records those values. Application source reads the
variables and does not embed the password.

## Data impact

May insert one `tenants` row and one `users` row on first start.

| Field          | Value                                             |
| -------------- | ------------------------------------------------- |
| Tenant name    | `VETOR`                                           |
| Tenant slug    | `vetor`                                           |
| Tenant id      | UUID generated by PostgreSQL                      |
| User email     | `admin@vetor.tech`                                |
| User profile   | `Administrador`                                   |
| User status    | `active`                                          |
| Password store | bcrypt hash only                                  |
| Existence key  | tenant slug `vetor` plus email `admin@vetor.tech` |

Does not change the approved portal entity shapes. Does not persist the
plaintext password. Does not replace UUID tenant ids with numbers.

## Security

- Do not hardcode `god@2025` or any password in `backend/` source.
- Hash with bcrypt at cost 12, matching the current portal reset path.
- Do not log the password, the hash, or JWT secrets.
- Production also seeds the user. The production password must come from
  environment or secret storage. The local example value is a known default
  and must be changed in shared and production environments.
- Existence check is scoped to tenant slug `vetor` and email
  `admin@vetor.tech` so a duplicate `Administrador` is not inserted on every
  restart.
- The bootstrap user is an operator account, not a public marketing identity.
